# Коннекторы: из `lib/crm.ts` в три подключаемых интеграции

Задел под то, что вы описали: «вставил ключ → попробовал смапить поля → поправил →
поехали». Текущий флоу не трогается — он продолжает работать как есть, пока не будет
готов и проверен новый.

---

## Что мешает прямо сейчас

`src/lib/crm.ts` — 900+ строк, и в нём смешаны три разные вещи:

1. **Транспорт** — HTTP к RetailCRM, ключи из env, выбор ключа по `shop === 'kaktusfiori'`.
2. **Маппинг** — `mapCrmOrder`, `parseSlot`, `CRM_STATUS_MAP`, разбор адреса.
3. **Доменная логика** — геокодинг, зоны, расчёт себестоимости, upsert заказа, уведомления.

Третий пункт от CRM не зависит вообще: он одинаков для RetailCRM, Битрикса и любого
вебхука. Первые два — как раз то, что должно стать сменным.

Плюс сейчас ключи выбираются жёстко:

```ts
const isMeura = orderInDb?.shop === 'kaktusfiori' || orderInDb?.shop === 'meura-flowers';
const apiKeyToUse = isMeura ? CRM_KEY_MEURA : CRM_KEY;
```

Каждый новый магазин — это правка кода и деплой. Модель `Connector` из патча схемы
переносит ключ, URL и маппинг в базу, и добавление магазина становится действием в админке.

## Целевая структура

```
src/lib/connectors/
  types.ts        общий интерфейс + типы NormalizedOrder / ConnectorResult
  registry.ts     выбор коннектора по shop.connectorType
  retailcrm.ts    перенос текущей логики RetailCRM (без изменений поведения)
  bitrix24.ts     новый
  webhook.ts      универсальный приём JSON (уже частично есть в /api/webhooks)
  mapping.ts      применение fieldMap/statusMap из Connector.fieldMap

src/lib/crm.ts    остаётся: геокодинг, зоны, calcBaseDeliveryPrice, upsertOrder,
                  notify — то есть всё, что не зависит от источника заказов
```

### Общий интерфейс

```ts
// src/lib/connectors/types.ts
export type NormalizedOrder = {
  externalId: string;
  address: string | null;
  slotRaw: string | null;
  price: number | null;
  items: string | null;
  comment: string | null;
  customerName: string | null;
  customerPhone: string | null;
  recipientName: string | null;
  recipientPhone: string | null;
  crmStatus: string | null;
  createdAt: Date | null;
};

export interface DeliveryConnector {
  type: "RETAILCRM" | "BITRIX24" | "WEBHOOK";
  /** Проверка ключа: дергаем самый дешёвый метод API */
  test(cfg: ConnectorConfig): Promise<{ ok: boolean; error?: string }>;
  /** Забрать заказы за период */
  fetchOrders(cfg: ConnectorConfig, since: Date): Promise<NormalizedOrder[]>;
  /** Отдать статус/курьера обратно */
  pushStatus(cfg: ConnectorConfig, externalId: string, patch: StatusPatch): Promise<void>;
  /** Сырой объект заказа — для экрана маппинга полей */
  sample(cfg: ConnectorConfig): Promise<Record<string, unknown> | null>;
}
```

`upsertOrder` в `lib/crm.ts` начинает принимать `NormalizedOrder` вместо `CrmOrder`,
и на этом связь с конкретной CRM заканчивается.

## Экран подключения (что видит компания)

Четыре шага, каждый — отдельное состояние `Connector`:

| Шаг | Что происходит | Поле в БД |
|---|---|---|
| 1. Выбор системы | RetailCRM / Битрикс24 / Вебхук | `type` |
| 2. Ключ и адрес | вставляют URL и API-ключ, жмут «Проверить» → `connector.test()` | `baseUrl`, `apiKey` |
| 3. Маппинг полей | тянем один реальный заказ через `sample()`, показываем его поля слева и наши справа | `fieldMap` |
| 4. Статусы | их статусы → наши `OrderStatus` | `statusMap` |

Ключевое на третьем шаге: **автоподбор с ручной правкой**. Сначала пытаемся угадать по
именам (`delivery.address.text` → `address`, `customerComment` → `comment`), показываем
результат с пометкой «угадано», человек правит спорное и пропускает ненужное. Без этого
экран превращается в форму на тридцать пустых полей, которую никто не заполнит.

Обязательными делаем только два поля — `externalId` и `address`. Всё остальное
опционально: без слота заказ просто не встанет в маршрут по времени, без состава курьер
не увидит, что везёт, но система работает.

## Порядок работ

1. **Вынести `retailcrm.ts`** — механический перенос текущего кода под интерфейс,
   поведение не меняется. Проверяется тем, что поллинг продолжает работать.
2. **Переключить чтение ключей** с env на `Shop.crmKey` с фолбэком на env
   (`shop.crmKey ?? process.env.CRM_KEY`) — так ничего не ломается до заполнения базы.
3. **Экран подключения** в админке магазина — шаги 1–2, без маппинга: для RetailCRM
   маппинг уже зашит в код.
4. **`webhook.ts` + маппинг** — самый ценный коннектор, потому что закрывает
   «любую CRM» из вашего оффера на лендинге.
5. **`bitrix24.ts`** — сделки через `crm.deal.list`, поля адреса из пользовательских
   полей сделки. Здесь маппинг обязателен: у каждого портала свои `UF_CRM_*`.

Идти в этом порядке важно: первые два пункта не меняют поведения и их можно
раскатывать на прод спокойно, а четвёртый и пятый уже трогают живые заказы.

## Что учесть заранее

- **Идемпотентность.** Повторный вебхук по тому же заказу не должен создавать дубль —
  ключ `@@unique([shopId, crmId])` из патча схемы это гарантирует на уровне базы.
- **Ошибки коннектора.** `Connector.errorCount` растёт при каждом падении; после
  N подряд коннектор выключается сам и в админке загорается предупреждение. Иначе
  сломанный ключ будет молча долбить чужой API тысячами запросов в сутки.
- **Секреты.** `apiKey` в базе стоит шифровать (хотя бы AES с ключом из env), а не
  хранить открытым текстом — база с ключами от чужих CRM это заметно более
  чувствительный актив, чем база заказов.
- **Лимиты.** У RetailCRM есть ограничение на частоту запросов, и оно на аккаунт,
  а не на ваш сервер. При десятке подключённых магазинов поллинг нужно разносить
  по времени, а не дёргать все разом в одну секунду.
