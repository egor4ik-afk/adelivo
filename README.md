## Как это работает

### Вход для компании

Отдельной регистрации «для компаний» не делал — она не нужна: вход по почте
уже есть и создаёт пользователя. Логика такая:

1. Человек входит обычным способом на `/login`.
2. Открывает `/company`. Компании у него нет → видит форму создания:
   название, адрес (`adelivo.ru/magaz`), телефон.
3. После создания он становится `ADMIN` **своей** компании — это и есть
   «локальный админ» из нашей схемы. Глобальным (`isSuperAdmin`) он не становится.
4. Получает ссылку-приглашение `adelivo.ru/join/magaz?t={токен}`. Кто входит
   по ней — попадает в его компанию.

Токен в ссылке обязателен: без него `/join/magaz` можно было бы подобрать,
зная название компании, и записаться в чужую фирму. Ссылку можно отозвать —
`PATCH /api/company` с `regenerateInvite`, старая перестаёт работать сразу.

### Подключение магазина

Внутри `/company` → «+ Магазин» → выбор системы → «Настроить»:

| Система | Что вводят | Чем проверяется |
|---|---|---|
| **RetailCRM** | адрес CRM + API-ключ | `GET /api/v5/orders?limit=20` — показывает количество заказов |
| **Битрикс24** | адрес входящего вебхука (токен уже в нём) | `crm.deal.fields` + `crm.deal.list` — показывает количество сделок |
| **1С** | адрес OData + `логин:пароль` | `GET /$metadata` с Basic-авторизацией — показывает количество объектов |
| **Свой вебхук** | ничего | токен генерируется сразу, ждём первый входящий заказ |

Кнопка «Проверить подключение» делает один читающий запрос и **ничего не меняет**
в вашей системе. Ошибки разобраны по кодам: 401 — неверный пароль, 403 — прав
не хватает, 404 для 1С — OData не опубликован на веб-сервере, и так далее.
Общее «что-то пошло не так» тут бесполезно: девять из десяти проблем при подключении —
это именно права и публикация.

Ключ в поле пароля можно оставить пустым при повторном сохранении — тогда он
не перезаписывается. Иначе нельзя было бы поправить адрес, не вводя ключ заново.
